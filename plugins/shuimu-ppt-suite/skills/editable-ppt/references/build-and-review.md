# 原生组装、验收与局部修改

## 构建方式

在项目中保留 `source/build_deck.mjs`；通过当前 presentations Skill 加载 runtime 与 API 文档，
调用 @oai/artifact-tool。只实现本次页面需要的对象；不创建自己的通用 PPT 引擎或静默切换图像模式。
生成的项目源码从 layout.json 读取内容与布局，不在脚本中再维护一份不同的文字副本。

按 z 从低到高建立对象：背景/色带 → 连线 → 图片/节点 → 原生文字/标签。connector 的逻辑端点以
设计对象 ID 定位，使用原生连接线；若连接符必须在节点存在后创建，创建后调整层级使其位于节点后方。
形状、文本、图片、表格、图表各自可选取；可按逻辑分组，但不能把分组渲染成单张图片。

用于审计的元素名称来自设计 ID；图表使用原生标题/轴/图例/数据标签而非额外假标签，以保证改数据后
正常更新。表格保留逐格编辑，注意合并单元格在审计中的映射（需要时扩展检查器并保留原始二维数据）。
复杂科学插图中的像素图本身不可编辑，但描述文字与指示线可编辑。对必须保持原貌的真实截图不要擦除
内部文字；在素材表和交付说明中明确例外。

## 代表页先验证

先组装一页含标题、正文、图片素材和简单流程的代表页，再组装一页表格或图表（材料中有才需要）。
核对实际渲染的字体、位置、裁切和文本长度，再批量组装其余页。该步骤默认由执行者自检，不要求用户
另行批准。如果模型图片本身布局不合适，只调整或重生成该素材，不把全页退回图片版。

## 三项验收

1. 设计一致：全部 ID 都有对象，文字与设计一致，素材已接受，所有表格数值/图表类别和单位与源数据一致。
2. 真实可编辑：运行 validate_deck.py --pptx，标题/正文必须存在于原生 p:sp 文本、table 必须是 a:tbl、
   chart 必须是原生 c:chart 引用；不能用隐藏/透明文字叠在整页图上。检查器无法判断所有视觉遮挡，
   还应在渲染中确认可见正文确由原生层承担。
3. 视觉正确：遵循 presentations finalization 渲染全部页面，检查溢出、遮挡、字体替换、图片变形、
   图表标签、表格边界；预期文字覆在色条上不算错误，正文被照片压住则必须修复。

在测试副本中把一个标题改为近似长度的新标题，用相同素材重建并确认新文案可见、图像无须重新生成。
同时检查一处表格单元格或图表值（存在时）。文件结构与重建测试不等价于在 Microsoft PowerPoint
界面中完成编辑；没有做真实应用内验证时如实说明。

## 修改路径

- 改字/数字：更新逐页文案、排版文档和 layout.json 中对应元素，重新组装相关页面，无须调用 image_gen。
- 改字号/对齐/位置：只修改对应元素样式与 box，保持 asset_id。
- 改照片/插画：保留 ID，更新文件版本及裁切，再组装和检查受影响页。
- 改图表/表格：更新真实数据及原生对象，不替换成截图。
- 用户直接在 PPT 中修改后再交回：优先读取现有 PPT 对象编辑，不能使用过时 JSON 覆盖用户新修改。

交付时提供可编辑 PPTX、三份设计 Markdown、layout.json、素材目录和构建源码。原图内部像素与源截图
内嵌文字不可逐项修改，这是明确的素材边界。可额外导出 PDF 供浏览，不能以 PDF 替代可编辑文件。
